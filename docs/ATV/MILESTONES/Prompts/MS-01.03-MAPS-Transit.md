# MS-01.03: Transit Overlay (M.A.P.S Framework)

## Mission
**Core objective:** Integrate MARTA (Metropolitan Atlanta Rapid Transit Authority) real-time transit data into the Atlanta FIFA Navigator, rendering bus and train locations as interactive markers on the map to enable users to make informed public transportation decisions during FIFA events.

**Problem statement:** Users attending events at Mercedes-Benz Stadium need real-time visibility into MARTA bus/train positions to:
- Determine if transit is viable alternative to driving (compare with traffic layer from MS-01.02)
- Plan departure times based on actual vehicle proximity to their location
- Avoid waiting at stations during service gaps or delays

**Solution approach:** Build secure backend API proxy (`/api/marta`) to fetch data from MARTA API, implement client-side SWR hook for data fetching with automatic revalidation, render vehicle markers on Google Maps with custom icons differentiating buses/trains.

**Mission-critical requirements:**
- API key security: MARTA_API_KEY stored server-side only, never exposed to client
- Performance: API route responds in <500ms (P95 latency)
- Resilience: Graceful degradation when MARTA API unavailable (503 response, UI fallback message)
- Data freshness: Poll MARTA API every 30 seconds via SWR revalidation

## Audience
**Primary audience: Event attendees using public transportation**
- User personas: Local residents familiar with MARTA, tourists unfamiliar with Atlanta transit, accessibility-dependent travelers requiring predictable transit times
- User needs: Real-time vehicle locations, distinction between bus/rail options, visual confirmation transit is running before leaving for stadium
- Context of use: Mobile devices (70% expected traffic), potentially limited connectivity in transit stations, high cognitive load during event rush

**Secondary audience: Development team (next milestone implementers)**
- Consumers of this work: MS-02.01 (i18n integration will need transit data localized), MS-03.01 (database may cache transit data)
- Integration points: Map component receives new marker data, SWR pattern establishes data-fetching convention for future APIs
- Maintenance considerations: MARTA API contract may change, error handling must be robust

**Output recipients:**
- **UI layer (components/Map.tsx):** Consumes array of transit vehicles with lat/lng coordinates, renders markers
- **Data layer (hooks/useMartaData.ts):** Provides typed vehicle data, loading states, error states to consuming components
- **API layer (app/api/marta/route.ts):** Proxies requests to MARTA API, returns normalized GeoJSON or custom vehicle schema

### Constraints & Requirements
**API route constraints (app/api/marta/route.ts):**
- MUST validate MARTA_API_KEY presence at runtime (throw error if missing)
- MUST implement timeout (abort request after 400ms to stay under 500ms budget including processing)
- MUST validate upstream response with Zod schema (catch malformed data early)
- MUST normalize MARTA API response to consistent internal schema:
  ```typescript
  interface TransitVehicle {
    id: string;
    type: 'bus' | 'train';
    latitude: number;
    longitude: number;
    route: string;
    heading?: number; // Optional: vehicle direction for future arrow icons
  }
  ```
- MUST return appropriate HTTP status codes:
  - 200: Success with vehicle data
  - 503: Upstream MARTA API unavailable (per docs/ATV/Guardrails.md fallback behavior)
  - 500: Unexpected server error (log to console for debugging)

**SWR hook constraints (hooks/useMartaData.ts):**
- Fetch from `/api/marta?type=bus` and `/api/marta?type=train` (or combined endpoint)
- Refresh interval: 30 seconds (balance data freshness vs. API rate limits)
- Error retry strategy: 3 retries with exponential backoff (1s, 2s, 4s delays)
- Return typed data matching TransitVehicle interface
- Expose loading, error states for UI consumption

**Map rendering constraints (components/Map.tsx):**
- MUST render distinct icons for buses vs. trains (visual differentiation)
- MUST handle empty data gracefully (no markers if data array empty)
- MUST display "No transit data available" message when API returns empty or errors
- SHOULD implement marker clustering if vehicle count >50 (performance optimization)
- Icon size: 32x32px for visibility at default zoom level
- Marker click interaction (optional stretch): Show tooltip with route name

### Data Schema Specifications
**Zod schema for MARTA API validation:**
```typescript
import { z } from 'zod';

const MartaVehicleSchema = z.object({
  id: z.string(),
  latitude: z.number().min(-90).max(90),
  longitude: z.number().min(-180).max(180),
  type: z.enum(['bus', 'train']),
  route: z.string(),
  heading: z.number().optional(),
});

const MartaResponseSchema = z.object({
  vehicles: z.array(MartaVehicleSchema),
});

export type TransitVehicle = z.infer<typeof MartaVehicleSchema>;
```

**SWR hook type signature:**
```typescript
interface UseMartaDataReturn {
  vehicles: TransitVehicle[] | undefined;
  isLoading: boolean;
  isError: boolean;
  error: Error | undefined;
}

function useMartaData(): UseMartaDataReturn;
```
