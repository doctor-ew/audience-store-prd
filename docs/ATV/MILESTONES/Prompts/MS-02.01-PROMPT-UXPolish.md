# MS-02.01: User Experience Polish (P.R.O.M.P.T Framework)

## Problem
**Problem statement:** Atlanta FIFA Navigator currently serves only English-speaking users, excluding 13% of Atlanta's population who primarily speak Spanish (per 2020 Census data). During international FIFA events, this barrier compounds as global attendees expect multilingual interfaces. Additionally, user preferences (language selection) reset on each visit, creating friction and degraded UX.

**User pain points:**
1. **Spanish-speaking users:** Cannot understand UI labels, button text, error messages → abandon app, rely on less optimal navigation methods
2. **Tourists from Latin America:** Expect Spanish support at international events → perceive app as unwelcoming, incomplete
3. **Preference persistence:** Users who switch to Spanish must re-select language on every page load → frustration, increased cognitive load
4. **Accessibility:** Screen reader users in Spanish need properly localized aria-labels and announcements

**Business impact:**
- Reduced adoption among 13% of target demographic (Spanish speakers)
- Missed PRD success metric: "Support for bilingual users (English/Spanish)"
- Negative social media sentiment if discovered during high-profile FIFA events
- Competitive disadvantage vs. multilingual navigation apps (Google Maps supports 40+ languages)

**Current state limitations:**
- All UI strings hardcoded in English within component JSX
- No translation infrastructure (i18next not configured)
- No preference storage mechanism (user selections ephemeral)
- No testing for multilingual accessibility compliance

## Requirements
**Must-have functional requirements:**
1. **Language switching capability**
   - User can toggle between English (en) and Spanish (es) via UI control
   - Language change applies immediately without page reload (client-side state update)
   - All UI text updates: headings, buttons, labels, error messages, tooltips
   - Google Maps remains in user's browser language (Maps API respects navigator.language)

2. **Preference persistence**
   - Language selection saved to browser localStorage
   - Preference auto-loaded on subsequent visits (check localStorage on app mount)
   - Fallback to browser language (`navigator.language`) if no saved preference
   - Default to English if browser language not supported (only en/es available)

3. **Translation coverage**
   - Minimum viable translations:
     - Page title/metadata: "Atlanta FIFA Navigator"
     - Map controls: "Toggle Traffic", "Transit Data", "Zoom In", "Zoom Out"
     - Status messages: "Loading map...", "No transit data available", "Error loading data"
     - Accessibility labels: All aria-labels translated
   - Future-proof structure: Organized JSON files enabling easy addition of Portuguese, French

4. **Accessibility compliance (WCAG 2.1 AA in both languages)**
   - Screen reader announcements in selected language
   - Language switcher keyboard-accessible (Tab, Space/Enter)
   - Language attribute updates on <html> tag (lang="en" or lang="es") for correct screen reader pronunciation
   - No text truncation or layout breaks in Spanish (often 20-30% longer than English)

**Must-have non-functional requirements:**
1. **Performance:** No degradation in page load speed (lazy-load translation files, <500ms to apply translations)
2. **Maintainability:** Centralized translation files (avoid scattered translation logic across components)
3. **Developer experience:** Simple API for adding new translations (`t('key.path')` syntax)
4. **Testability:** Translation keys validated at build time (fail build if missing translation)

**Must-NOT requirements (scope control):**
- Do NOT implement language auto-detection via geolocation (privacy concerns, unreliable)
- Do NOT translate dynamic content from MARTA API (focus on UI strings only)
- Do NOT add languages beyond English/Spanish in this milestone
- Do NOT build admin interface for managing translations (edit JSON files directly)

## Objectives
**Primary objective:** Deliver production-ready bilingual support (English/Spanish) with persistent user preferences, ensuring equal UX quality across both languages and maintaining WCAG 2.1 AA accessibility standards.

**Specific goals:**
1. **Inclusivity goal:** Enable 100% of Spanish-speaking Atlanta residents to use the app in their preferred language
2. **Retention goal:** Persist language preference across sessions, reducing user effort by 2 clicks/visit
3. **Accessibility goal:** Maintain Lighthouse Accessibility score of 100 in both English and Spanish
4. **Foundation goal:** Establish i18n architecture enabling rapid addition of Portuguese/French in future milestones

**Success indicators:**
- User can complete full journey (view map, toggle traffic, check transit) entirely in Spanish
- Language preference persists across browser sessions (localStorage read/write verified)
- Translation coverage: 100% of visible UI strings (no English leakage in Spanish mode)
- Automated tests validate both language modes (Jest assertions for translation rendering)

## Methods
**Approach: i18next + react-i18next library**

**Why i18next:**
- Industry standard for React i18n (47k+ GitHub stars, battle-tested)
- Built-in features: Lazy loading, pluralization, interpolation, nested keys
- React hooks integration (`useTranslation`) for ergonomic API
- Server-side rendering support (Next.js compatible)
- Minimal bundle size impact (~10KB gzipped with react-i18next)

**Implementation strategy:**

### Step 1: i18next Configuration (i18n.js)
```javascript
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import LanguageDetector from 'i18next-browser-languagedetector';

i18n
  .use(LanguageDetector) // Auto-detect from localStorage, navigator
  .use(initReactI18next)
  .init({
    resources: {
      en: { translation: require('./public/locales/en/common.json') },
      es: { translation: require('./public/locales/es/common.json') },
    },
    fallbackLng: 'en',
    supportedLngs: ['en', 'es'],
    detection: {
      order: ['localStorage', 'navigator'],
      caches: ['localStorage'],
    },
    interpolation: {
      escapeValue: false, // React handles XSS
    },
  });

export default i18n;
```

### Step 3: LanguageSwitcher Component (components/LanguageSwitcher.tsx)
```typescript
import { useTranslation } from 'react-i18next';
import { Globe } from 'lucide-react'; // Icon

export function LanguageSwitcher() {
  const { i18n } = useTranslation();

  const toggleLanguage = () => {
    const newLang = i18n.language === 'en' ? 'es' : 'en';
    i18n.changeLanguage(newLang);
    document.documentElement.lang = newLang; // Update <html lang>
  };

  return (
    <button
      onClick={toggleLanguage}
      aria-label={`Switch to ${i18n.language === 'en' ? 'Spanish' : 'English'}`}
      className="flex items-center gap-2 px-4 py-2 bg-white rounded-lg shadow hover:bg-gray-50"
    >
      <Globe size={20} />
      <span className="font-medium">
        {i18n.language === 'en' ? 'ES' : 'EN'}
      </span>
    </button>
  );
}
```

### Step 5: Preference Management Hook (store/usePreferences.ts)
```typescript
import { useEffect } from 'react';
import { useTranslation } from 'react-i18next';

export function usePreferences() {
  const { i18n } = useTranslation();

  useEffect(() => {
    // i18next LanguageDetector handles localStorage automatically
    // This hook can be extended for other preferences in future
  }, []);

  const setLanguage = (lang: 'en' | 'es') => {
    i18n.changeLanguage(lang);
    document.documentElement.lang = lang;
  };

  return {
    currentLanguage: i18n.language,
    setLanguage,
  };
}
```

### Step 6: Update Layout (app/layout.tsx)


## Parameters
**Scope boundaries:**
- **In scope:** UI string translations, language switcher component, localStorage persistence, HTML lang attribute updates, accessibility testing in both languages
- **Out of scope:** Backend data localization (MARTA API responses remain English), third-party content (Google Maps UI), user accounts/authentication

**Technical constraints:**
- **Library versions:** i18next ^23.0.0, react-i18next ^13.0.0, i18next-browser-languagedetector ^7.0.0
- **Bundle size budget:** Total i18n overhead <15KB gzipped (verify with webpack-bundle-analyzer)
- **Language codes:** ISO 639-1 (en, es) for consistency with standard
- **Translation format:** JSON only (no YAML, PO files)

**Performance constraints:**
- Translation file load: <100ms (translations bundled with app, not lazy-loaded initially)
- Language switch time: <50ms (setState operation, no async loading)
- No layout shift when switching languages (test with longer Spanish strings)

**Accessibility constraints:**
- Language switcher must be in page header (persistent access)
- Min 44x44px touch target for mobile users
- Focus indicator meets 3:1 contrast ratio
- Screen reader announces language change (aria-live="polite" region)

**Content constraints:**
- Translation quality: Native speaker reviewed (use professional translator or fluent team member, not Google Translate alone)
- Maintain tone: Formal/professional (addressing stadium attendees, not casual chat)
- Terminology consistency: Use MARTA's official Spanish terms (e.g., "tren" not "metro")

## Testing
**Unit testing (tests/LanguageSwitcher.test.tsx):**
```typescript
import { render, screen, fireEvent } from '@testing-library/react';
import { LanguageSwitcher } from '../components/LanguageSwitcher';
import { I18nextProvider } from 'react-i18next';
import i18n from '../i18n';

describe('LanguageSwitcher', () => {
  it('renders current language code', () => {
    render(<I18nextProvider i18n={i18n}><LanguageSwitcher /></I18nextProvider>);
    expect(screen.getByText(/EN|ES/)).toBeInTheDocument();
  });

  it('switches language on click', () => {
    render(<I18nextProvider i18n={i18n}><LanguageSwitcher /></I18nextProvider>);
    const initialLang = i18n.language;
    fireEvent.click(screen.getByRole('button'));
    expect(i18n.language).not.toBe(initialLang);
  });

  it('updates HTML lang attribute', () => {
    render(<I18nextProvider i18n={i18n}><LanguageSwitcher /></I18nextProvider>);
    fireEvent.click(screen.getByRole('button'));
    expect(document.documentElement.lang).toMatch(/en|es/);
  });

  it('is keyboard accessible', () => {
    render(<I18nextProvider i18n={i18n}><LanguageSwitcher /></I18nextProvider>);
    const button = screen.getByRole('button');
    button.focus();
    expect(document.activeElement).toBe(button);
    fireEvent.keyDown(button, { key: 'Enter' });
    // Language should toggle
  });
});
```
