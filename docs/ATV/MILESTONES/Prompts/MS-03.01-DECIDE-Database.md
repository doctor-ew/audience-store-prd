# MS-03.01: Database Integration (D.E.C.I.D.E Framework)

## Define
**Decision to make:** Select and implement persistent database solution for user preferences (language, favorites, future personalization settings), replacing ephemeral localStorage from MS-02.01.

**Problem context:**
- **Current limitation:** User preferences stored in browser localStorage (MS-02.01) → data loss when user clears browser data, no cross-device sync, no server-side analytics on user behavior
- **Scale consideration:** MVP targets 10,000 users during FIFA event week → localStorage adequate for single-device experience but fails for users switching between mobile/desktop
- **Future requirements:** Roadmap includes user accounts, saved routes, event notifications → requires server-side user profile storage
- **Technical debt risk:** Keeping localStorage long-term creates migration pain later (data backfill complexity, dual-write periods)

**Why this matters now:**
1. **Cross-device consistency:** Users who set language preference on mobile expect same preference on desktop (30% of users use multiple devices per Google Analytics benchmarks)
2. **Data durability:** Browser clears/private mode erase localStorage → poor UX, support burden
3. **Analytics foundation:** Cannot track preference trends (% Spanish users, favorite teams) without server-side storage
4. **Authentication readiness:** Database integration prerequisite for future Firebase Auth (MS-04.x roadmap item)

**Key constraints from docs/ATV/TECH_SPEC.md:**
- Primary database: Firebase (Firestore) specified in architecture section
- Local development: SQLite with Prisma ORM for prototyping
- Deployment: Vercel (serverless functions → database connection pooling considerations)
- Security: API keys stored as Vercel environment variables, never client-exposed

**Decision scope:**
- **In scope:** Database provider selection, schema design for UserPreference model, API route implementation (GET/POST), migration from localStorage, integration testing
- **Out of scope:** User authentication (no login required yet, use session IDs), real-time data sync (WebSockets), caching layers beyond SWR client-side

## Enumerate
**Option 1: Firebase Firestore (Specified in Tech Spec)**
- **Description:** Google's NoSQL cloud database, Document-oriented (collections of JSON-like documents)
- **Tech stack integration:** Firebase Admin SDK for server-side access via Next.js API routes
- **Pricing:** Free tier: 50K reads/day, 20K writes/day (sufficient for MVP 10K users)
- **Local development:** Firebase Emulator Suite for offline development
- **Authentication:** Firebase Auth native integration (future-proofing for MS-04.x)

**Option 2: Vercel Postgres (Vercel-native SQL database)**
- **Description:** PostgreSQL database provisioned/managed by Vercel, optimized for serverless
- **Tech stack integration:** @vercel/postgres SDK, Prisma ORM support
- **Pricing:** Free tier: 256 MB storage, 60 compute hours/month
- **Local development:** PostgreSQL via Docker, Prisma migrations
- **Authentication:** Separate auth provider required (e.g., Clerk, Auth0)

**Option 3: Continue with localStorage + Future Migration**
- **Description:** Defer database integration to post-MVP, accept localStorage limitations
- **Tech stack integration:** No backend changes, pure client-side
- **Pricing:** $0 (no cloud costs)
- **Local development:** Browser DevTools only
- **Authentication:** N/A (no server-side user identity)

**Option 4: Supabase (Open-source Firebase Alternative)**
- **Description:** PostgreSQL-based backend-as-a-service with realtime capabilities
- **Tech stack integration:** Supabase JS client, built-in auth
- **Pricing:** Free tier: 500 MB storage, unlimited API requests
- **Local development:** Supabase CLI with Docker
- **Authentication:** Supabase Auth (alternative to Firebase Auth)

**Option 5: Prisma + SQLite (Local) + Planetscale (Production)**
- **Description:** Hybrid approach - SQLite for development, Planetscale (MySQL) for production
- **Tech stack integration:** Prisma ORM abstracts database differences
- **Pricing:** Planetscale free tier: 1 database, 5GB storage, 1B row reads/month
- **Local development:** SQLite (file-based, zero config)
- **Authentication:** Separate provider required

## Investigate
**Option 1 Analysis: Firebase Firestore**

**Pros:**
- ✅ **Tech Spec alignment:** Explicitly specified as primary database (docs/ATV/TECH_SPEC.md line 27)
- ✅ **DX:** Excellent docs, simple query API, Firebase Admin SDK well-maintained
- ✅ **Vercel integration:** Official Vercel + Firebase guide, env var pattern established
- ✅ **Future auth:** Firebase Auth seamless integration (single provider for DB + auth)
- ✅ **Real-time:** Built-in real-time listeners (useful for future collaborative features)
- ✅ **Free tier:** 50K reads + 20K writes/day exceeds MVP needs (10K users × 2 writes = 20K/day)

**Cons:**
- ⚠️ **Vendor lock-in:** Firestore query syntax proprietary (hard to migrate off later)
- ⚠️ **Local dev:** Firebase Emulator requires Java runtime (adds setup complexity)
- ⚠️ **Cold starts:** Vercel serverless + Firebase Admin SDK initialization adds ~200ms latency first request
- ⚠️ **NoSQL constraints:** No JOIN operations (acceptable for simple preference data, but limiting for complex queries)

**Performance benchmark (simulated):**
- GET request (read user preference): ~150ms (Firestore read + Vercel function overhead)
- POST request (write preference): ~200ms (Firestore write + Vercel function overhead)
- **Verdict:** Meets <500ms requirement ✅

**Cost projection (10K users, 30-day period):**
- Reads: 10K users × 2 sessions/day × 1 read/session × 30 days = 600K reads/month (FREE tier: 1.5M reads/month) ✅
- Writes: 10K users × 2 sessions/day × 1 write/session × 30 days = 600K writes/month (FREE tier: 1M writes/month) ✅
- **Verdict:** $0 cost at MVP scale ✅

## Decide
**Selected Option: Firebase Firestore (Option 1)**

**Rationale:**
1. **Tech Spec compliance (25% weight, score 5):** Explicitly specified in docs/ATV/TECH_SPEC.md → architectural consistency
2. **Future-proofing (15% weight, score 5):** Firebase Auth integration trivial (same vendor, shared SDKs) → supports roadmap MS-04.x authentication milestone
3. **Cost (15% weight, score 5):** $0 at MVP scale, generous free tier scales to 100K users before billing
4. **Performance (10% weight, score 4):** 150-200ms API routes well under 500ms requirement, cold start acceptable for MVP
5. **DX (20% weight, score 4):** Excellent docs, simple API, minor downside of Java requirement for emulator mitigated by one-time setup
6. **Vercel integration (15% weight, score 4):** Well-documented pattern, official guides available

**Total weighted score: 4.55/5**

**Trade-offs accepted:**
- Vendor lock-in (Firestore proprietary) → mitigated by preference data simplicity (easy to export JSON, migrate if needed)
- NoSQL constraints → acceptable for user preferences (no complex JOINs required)
- Emulator Java dependency → one-time setup cost, amortized across team

**Alternatives rejected:**
- **Vercel Postgres:** Would score 3.8/5 (better performance, worse future-proofing due to auth separation)
- **Supabase:** Would score 3.5/5 (good features, but Tech Spec deviation + smaller ecosystem)
- **localStorage:** Scores 2.0/5 (fails cross-device, data durability criteria)

```typescript
import { db } from './firebase';
import { UserPreferenceInput, UserPreferenceSchema } from './schemas';

export async function getUserPreference(userId: string) {
  const docRef = db.collection('users').doc(userId);
  const doc = await docRef.get();

  if (!doc.exists) {
    return null;
  }

  return doc.data();
}

export async function setUserPreference(input: UserPreferenceInput) {
  const validated = UserPreferenceSchema.parse(input);

  const docRef = db.collection('users').doc(validated.userId);
  await docRef.set(
    {
      ...validated,
      updatedAt: new Date(),
    },
    { merge: true } // Update existing fields, preserve others
  );

  return validated;
}
```

### Phase 4: API Routes (Day 5)
**File: `app/api/preferences/route.ts`**
```typescript
import { NextRequest, NextResponse } from 'next/server';
import { getUserPreference, setUserPreference } from '@/lib/preferences';
import { UserPreferenceSchema } from '@/lib/schemas';

// GET /api/preferences?userId=xxx
export async function GET(request: NextRequest) {
  const { searchParams } = new URL(request.url);
  const userId = searchParams.get('userId');

  if (!userId) {
    return NextResponse.json(
      { error: 'Missing userId parameter' },
      { status: 400 }
    );
  }

  try {
    const preference = await getUserPreference(userId);

    if (!preference) {
      return NextResponse.json(
        { error: 'User not found' },
        { status: 404 }
      );
    }

    return NextResponse.json(preference, { status: 200 });
  } catch (error) {
    console.error('GET /api/preferences error:', error);
    return NextResponse.json(
      { error: 'Internal server error' },
      { status: 500 }
    );
  }
}

// POST /api/preferences
export async function POST(request: NextRequest) {
  try {
    const body = await request.json();
    const validated = UserPreferenceSchema.parse(body);

    const result = await setUserPreference(validated);

    return NextResponse.json(result, { status: 200 });
  } catch (error) {
    if (error instanceof z.ZodError) {
      return NextResponse.json(
        { error: 'Invalid request body', details: error.errors },
        { status: 400 }
      );
    }

    console.error('POST /api/preferences error:', error);
    return NextResponse.json(
      { error: 'Internal server error' },
      { status: 500 }
    );
  }
}
```

### Phase 5: Update Preferences Hook (Day 6)
**File: `store/usePreferences.ts` (refactor from MS-02.01)**
```typescript
import { useState, useEffect } from 'react';
import { v4 as uuidv4 } from 'uuid';

interface UserPreference {
  userId: string;
  language: 'en' | 'es';
  favorites: string[];
}

export function usePreferences() {
  const [userId, setUserId] = useState<string>('');
  const [preference, setPreference] = useState<UserPreference | null>(null);
  const [isLoading, setIsLoading] = useState(true);

  // Initialize userId from localStorage or generate new
  useEffect(() => {
    let storedUserId = localStorage.getItem('userId');
    if (!storedUserId) {
      storedUserId = uuidv4();
      localStorage.setItem('userId', storedUserId);
    }
    setUserId(storedUserId);
  }, []);

  // Fetch preference from API when userId available
  useEffect(() => {
    if (!userId) return;

    fetch(`/api/preferences?userId=${userId}`)
      .then(res => res.json())
      .then(data => {
        setPreference(data);
        setIsLoading(false);
      })
      .catch(err => {
        console.error('Failed to fetch preferences:', err);
        setIsLoading(false);
      });
  }, [userId]);

  const updateLanguage = async (language: 'en' | 'es') => {
    const updated = { ...preference, userId, language };

    await fetch('/api/preferences', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(updated),
    });

    setPreference(updated);
  };

  return {
    preference,
    isLoading,
    updateLanguage,
  };
}
```
